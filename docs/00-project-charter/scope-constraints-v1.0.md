# 项目范围与约束 v1.0

> 历史版本：当前范围见`scope-constraints-v1.1.md`。

## 项目目的

OfferLab 是一个校招岗位筛选与比较实验项目，保留从用户研究、需求定义、产品设计到 AI 评测、MVP 落地和版本迭代的完整过程。

## 成功定义

项目成功不以注册用户数、商业收入或线上流量衡量，而以以下结果衡量：

1. 有一个可以本地运行和演示的完整 MVP；
2. 产品决策能够追溯到用户研究；
3. AI 输出有评测数据和失败案例；
4. 至少完成一次小规模用户测试和一次迭代；
5. GitHub 仓库能够清楚记录产品方案、实现过程和实验结果。

## 产品范围

### 包含

- 2027 届应届生资格画像；
- 六家目标央企的少量公开岗位样本；
- 校招资格判断；
- 基于专业、经历和技能的岗位召回；
- 召回与资格判断的证据解释；
- 2–3 个岗位横向比较；
- 小规模测试与结果记录。

### 不包含

- 全网或实时岗位聚合；
- 生产级爬虫；
- 大规模用户账户系统；
- 自动网申和批量投递；
- 商业支付；
- 企业招聘端；
- 高并发与生产级运维；
- 无真实数据支持的录取概率预测。

## 资源约束

- 一人主导完成；
- 总周期 3 周；
- 默认每周投入 15–20 小时，总投入约 45–60 小时；
- 以现有 Python、SQL 能力为基础；
- 主要使用免费工具；
- 岗位数据由公开官网样本和人工核验组成；
- 用户测试规模为 3–5 人；
- 不要求长期部署；
- 不暴露受访者、作者或求职者的个人敏感信息。

## 需要展示的 AI 产品经理能力

- 用户需求调研；
- 场景和痛点拆解；
- 竞品分析与机会判断；
- MVP 范围控制；
- PRD 和交互流程；
- AI 能力边界设计；
- 评测集与指标设计；
- 跨角色任务拆解；
- 用户测试和数据复盘；
- 产品迭代与文档沉淀。

## 当前阶段

阶段 0：项目立项与范围确认已完成。

下一阶段为阶段 1：补齐用户研究记录和问题定义。在阶段 3 完成前，不扩大岗位数据采集或开始技术实现。

## 三周项目里程碑

### M1：第 7 天完成产品定义

- 用户问题有研究证据；
- 差异化有竞品依据；
- MVP PRD 和验收标准完成；
- 功能范围冻结。

### M2：第 14 天完成可运行 MVP

- 核心流程可本地运行；
- 至少 20 条脱敏岗位样本；
- AI 与规则分工落地；
- 无 API Key 时可以演示。

### M3：第 21 天完成 GitHub 作品集

- 完成离线评测和用户测试；
- 完成至少一次版本迭代；
- README、截图、案例说明和运行文档齐全；
- 仓库不含个人隐私、受访者身份或密钥。

## 范围冻结规则

进入第 2 周后，除非核心流程无法完成，否则不增加新功能。新增想法统一进入 `future-roadmap.md`，不进入三周版本。

## 停止规则

出现以下情况时停止继续扩展，并采用降级方案：

- 公开岗位页面无法稳定获取：改用人工整理的公开样本；
- API 成本或配置影响演示：改用预计算结构化结果；
- 原型测试显示用户不理解综合评分：删除综合分，只展示资格状态和证据；
- 时间落后两天以上：将目标企业缩减为三大运营商；
- 时间落后四天以上：岗位样本降至 20 条，用户测试保持 3 人。

## 预算

- 必需软件成本：0 元；
- 托管成本：0 元，本地演示；
- 大模型 API 建议上限：50 元；
- 其他付费工具：不采购；
- 总预算建议上限：50 元。
