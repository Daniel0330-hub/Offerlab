# OfferLab 项目章程 v1.0

## 1. 项目背景

应届生寻找校招岗位时，需要分别进入企业官网或综合招聘平台。企业官网分散，综合平台常将校招、实习和社招混合展示；同名岗位在不同公司的职责、专业限制和资格条件也存在差异。用户需要重复搜索、阅读和判断，难以快速形成可比较的候选岗位集合。

## 2. 项目目标

在 3 周内完成一个可本地运行的 AI 校招岗位筛选与比较实验产品，并将完整产品过程发布到 GitHub，用于证明作者具备 AI 产品经理所需的需求研究、方案设计、AI 能力边界、项目落地、评测和迭代能力。

## 3. 核心用户

第一用户为参加 2027 校园招聘、需要从多个企业官网寻找岗位的硕士应届生。种子用户背景为统计学硕士、精算学本科，掌握 Python 和 SQL，目标企业为三大运营商和三桶油。

## 4. 核心问题

如何帮助应届生从少量但来源可信的公开招聘样本中：

1. 排除明显不具备校招申请资格的岗位；
2. 找到与专业、经历和技能相关的岗位；
3. 理解岗位被召回或需要核实的原因；
4. 横向比较不同企业岗位的实际职责与门槛。

## 5. 产品假设

如果系统把岗位资格、职责主题和用户证据统一结构化，并将硬性资格与软性相关性分开呈现，那么用户找到并确认候选岗位所需的时间会减少，也更容易发现不同公司同名岗位之间的重要差异。

## 6. MVP

### 模块一：用户资格画像

记录毕业届次、学历、专业、技能、英语、地点和轮岗偏好。

### 模块二：岗位筛选与解释

针对 20–30 条公开岗位样本，输出 `符合资格`、`不符合` 或 `需要核实`，并引用 JD 原文；随后展示相关岗位和召回依据。

### 模块三：岗位横向比较

选择 2–3 个岗位，对比招聘单位、届次、学历、专业、地点、职责主题、能力证据、信息缺口和官方来源。

## 7. 非目标

- 建立商业化招聘平台；
- 全网岗位覆盖；
- 实时生产级爬虫；
- 自动投递；
- 大量用户运营；
- 录取概率预测；
- 替用户做最终投递决定。

## 8. 成功指标

### 产品指标

- 3 名以上用户完成核心任务；
- 核心任务完成率达到 80% 或记录具体失败原因；
- 与手动流程相比，找到并确认候选岗位的中位时间下降；
- 用户能正确理解三种资格状态；
- 用户能通过比较页指出至少一个原先忽略的岗位差异。

### AI 指标

- 招聘类型、届次、学历、专业、地点字段分别评测；
- 每条资格结论都有 JD 原文证据；
- 信息缺失时输出 unknown；
- 记录误放、误杀和证据引用错误；
- 公开评测样本、人工标准答案和失败案例。

### 作品集指标

- README 可在 5 分钟内讲清问题、方案和结果；
- 无 API Key 时可运行或查看完整演示；
- 至少展示一次有依据的版本迭代；
- 文档、代码、评测和演示相互一致。

## 9. 项目约束

- 周期：3 周；
- 人力：一人主导，AI 辅助；
- 时间：约 45–60 小时；
- 预算：不超过 50 元；
- 数据：20–30 条人工核验的公开岗位作为基线，可在进度允许时扩至 50 条；
- 用户测试：3–5 人；
- 运行方式：本地优先。

## 10. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 岗位页面难以稳定采集 | 数据准备延期 | 人工整理公开样本，不建设爬虫 |
| 需求不断增加 | 三周无法完成 | 第 7 天冻结范围，新想法进入未来路线图 |
| AI 输出不稳定 | 资格误判 | 强规则优先、证据引用、unknown 降级 |
| 用户测试组织困难 | 缺少验证 | 提前约 3 名朋友，第 2、3 周各测试一次 |
| API 配置影响演示 | GitHub 无法复现 | 保存预计算结果，API 作为可选能力 |
| 文档多于产品 | 演示效果弱 | 每份文档服务于一个决策，第二周必须完成可运行闭环 |
